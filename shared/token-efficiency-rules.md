# Token 效率准则（权威版本）

> 本文件是通用准则的唯一权威来源。两侧入口只保留各自环境特有的条款并指向这里：
> - Cursor 侧：`~/.cursor/rules/deepseek-speed.mdc`
> - Codex 侧：`~/.codex/skills/token-efficient-workflow/SKILL.md`
>
> 修改通用准则时只改本文件；改完请同步检查两侧入口是否仍只包含差异条款。
> 最后更新：2026-09-18

## 0. 核心规则

> 先少读，窄搜索，只打开需要的，然后摘要。输出保持简短。

## 1. 先给任务分级

- `simple`：小改动、短回答、单文件、低风险 → 不写长计划，不默认打开参考文档，直接执行
- `standard`：常规项目工作，涉及 1~3 个相关文件 → 用最小项目上下文，只验证关键点
- `deep`：调试、自动化、凭据、生产数据、多工具协作、敏感数据 → 先给短计划，分阶段执行，改动前后都验证，破坏性操作先获批准

## 2. 搜索优先于打开

- 先按精确关键词搜索，再决定打开哪个文件
- 先看文件名与小片段预览，避免整文件通读
- 不做递归目录转储，不整份读日志，不无理由加载导出、备份、数据文件

## 3. 避免噪声路径

除非任务明确需要，不读取、不搜索、不摘要以下内容：

```text
node_modules/  vendor/  dist/  build/  .next/  .nuxt/  coverage/  .cache/  tmp/  temp/  exports/  backups/  logs/
```

默认回避以下文件类型：

```text
.env  .env.*  *.log  *.zip  *.bak  *.sql  *.sqlite  *.db  *.csv  *.xlsx  *.xls
credentials.json  *token*.json  secrets.json
```

## 4. 日志处理

不要把大段日志原样粘贴或逐行处理。做法是：确认命令 → 提取第一段相关错误 → 最多保留 20~40 行有用内容 → 忽略重复堆栈 → 概括可能原因 → 给出下一步最小验证动作。

## 5. 最小 diff

只改必要部分。不做全局重排版、不顺手清理无关代码、不整文件重写，除非用户明确要求。

## 6. 最终输出格式

执行类任务的最终回复保持简短，可用以下结构：

```markdown
完成：
改动：
验证：
遗留/风险：
下一步：
```

## 7. 参考文档按需取用

把索引文件当地图，默认最多打开 1~3 个参考文件；用户明确要求深入研究时才扩大范围。

## 8. 排查顺序

先看日志 → 再看配置与环境 → 最后读代码，减少无效探索。

## 9. 等待不要靠猜时长

- 等命令/进程结束：前台阻塞或后台执行 + 完成通知，不要另加 sleep。
- 等外部条件（端口、文件、日志、服务就绪）：短间隔轮询（2~5 秒）并设上限，命中即停。
- 只有限流退避这类确实需要固定间隔的场景才 sleep，且时长有依据。
- 单次 sleep 超过约 30 秒、或同一等待重复超过两轮，就改成带上限的短轮询并说明在等什么。

依据与反例见 `skills/waiting-and-async/SKILL.md`。

## 10. 保持上下文前缀稳定

不要频繁改写全局规则、AGENTS.md 或已注入的技能文本。模型侧按前缀自动缓存，前缀稳定时命中缓存，响应更快、成本更低。一次性整改完成后即冻结这些文件。
