# 架构词汇与原则

改编自 Matt Pocock skills 的 codebase-design（MIT，见 ../LICENSE.txt）。中文说明，术语保留英文对照。

## 词汇（固定用法）

- **模块（module）**：任何有接口和实现的东西，不分大小：函数、类、包、跨层切片。不用“组件/服务/单元”。
- **接口（interface）**：调用方正确使用模块必须知道的一切：签名之外还有不变量、调用顺序、错误模式、必需配置和性能特征。
- **实现（implementation）**：模块内部的代码。与“适配器”不同：小适配器可以有大实现（Postgres 仓储），大适配器可以有小实现（内存假实现）。
- **深度（depth）**：接口处的杠杆，即调用方或测试每学一单位接口能用上多少行为。小接口藏大量行为为“深”，接口几乎和实现一样复杂为“浅”。
- **接缝（seam）**（Michael Feathers）：不改此处代码就能替换行为的位置，也就是接口所在处。接缝放在哪里，与接缝后面放什么，是两个独立决定。不用“边界”。
- **适配器（adapter）**：在接缝处满足接口的具体实现，描述角色而非内容。
- **杠杆（leverage）**：调用方从深度得到的好处：一处实现回报 N 个调用点和 M 个测试。
- **局部性（locality）**：维护者从深度得到的好处：变更、缺陷、知识和验证集中在一处，修一次全处生效。

## 原则

- **深度是接口的属性**：深模块内部可以由小而可替换的部件组成，只要它们不出现在接口上。内部接缝供自身测试用，不必暴露。
- **删除测试**：假设删掉模块。复杂度随之消失，它只是转发；复杂度散回 N 个调用方，它在挣钱。
- **接口就是测试面**：调用方和测试走同一个接缝。想绕过接口去测，多半是模块形状错了。
- **一个适配器是假设的接缝，两个才是真的**：没有东西真的在接缝两侧变化（通常是生产 + 测试），就不要引入 port，那只是间接层。
- 不按“实现行数 / 接口行数”衡量深度，那会奖励注水；按杠杆衡量。

## 可测试的接口

1. 接收依赖而不是在内部创建（`process(order, gateway)` 优于在函数里 `new StripeGateway()`）。
2. 返回结果而不是产生副作用（`calculateDiscount(cart) -> Discount` 优于直接改 `cart.total`）。
3. 表面积小：方法越少需要的测试越少，参数越少测试准备越简单。

## 依赖类别（决定怎样跨接缝测试）

1. **进程内**：纯计算、内存状态、无 I/O。总能加深：合并模块，直接通过新接口测试。
2. **本地可替身**：有本地替身（PGLite、内存文件系统）。在测试里跑替身，接缝留在内部，不在外部接口加 port。
3. **远程但自有**（ports & adapters）：自己的跨网络服务。在接缝定义 port，深模块持有逻辑，传输作为适配器注入；测试用内存适配器，生产用 HTTP/gRPC/队列适配器。
4. **真正外部**：不受控的第三方服务。作为注入的 port，测试提供 mock 适配器。

## 测试策略：替换，不叠加

- 深化后的模块接口上有了测试，旧的浅模块单元测试就是负担，删掉。
- 测试断言通过接口可观察的结果，不断言内部状态；内部重构后测试应不需改动。

## 设计两次（比较接口方案）

先给用户写清问题空间：新接口须满足的约束、依赖及其类别、一段只为说明约束的示意代码。随后给每个独立子代理同一份技术简报（文件路径、耦合细节、依赖类别、接缝后放什么、项目领域词汇），但各自不同的约束：

- 最小化接口：1~3 个入口，每个入口杠杆最大。
- 最大化灵活性：支持多用例和扩展。
- 优化最常见调用方：让默认用法最简单。
- （适用时）围绕跨接缝依赖设计 ports & adapters。

每版输出：接口（类型、方法、参数、不变量、顺序、错误模式）、调用示例、接缝后隐藏了什么、依赖与适配器策略、取舍。逐个呈现后按深度、局部性和接缝位置比较，给出明确推荐；不同方案的长处能结合时提出混合方案。
