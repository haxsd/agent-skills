# 等待与异步：不要猜时长

命令的耗时要么被观测，要么不存在。凭感觉挑一个 sleep 时长，是按猜测付账：

- 猜短了条件还没满足，只能再睡一轮。
- 猜长了就算条件早已满足，也要睡满。**这不是 token 成本，是纯墙钟浪费**，而且失败会被「睡够时间了，假设它好了」掩盖。

先分清在等什么，再决定怎么等：

- **等进度**：某个命令/进程结束 → 用前台阻塞或完成通知，**不要 sleep**。
- **等条件**：端口就绪、文件出现、日志出现某行 → 短轮询，命中即停。
- **等固定时长**：限流退避、协议要求的间隔 → 才 sleep，且时长有依据。

| 情形 | 做法 |
|---|---|
| 短命令，且你要它的结果才能往下走 | 前台执行，阻塞到结束；**不要**再补一个 sleep |
| 长命令，等它结束 | 前台执行 + 合理超时；转后台后让完成通知叫醒你 |
| 长命令，等待期间有别的事做 | 后台执行，先干别的；完成通知会到 |
| 等外部条件（端口/文件/日志） | 短间隔轮询 + 上限，命中即停 |
| 真要等一段固定时间（限流退避） | 才 sleep，且时长有依据 |

## 规则

1. **前台阻塞就是等待方式。** 你要结果才能继续，就直接跑；跑完自然返回，不需要任何 sleep。超时值只是保险丝：设「不应该超过」的上限，别为了保险放大它。
2. **完成通知通常已经存在——先用 10 秒探针验证，再决定要不要睡。** 起一个 10 秒任务、不做任何轮询，看完成通知是否自己到达。有通知 → 不需要 sleep；没有 → 按第 3 条轮询。注意通知按自身时机送达，不保证你刚想检查时立刻到；手上没别的事时，让轮次结束、等通知或条件就绪，也比睡满一个猜测时长好。
3. **必须轮询就短轮询，锚定真实条件。** 间隔 2~5 秒（最慢 10 秒），条件满足立刻停，并设一个上限：

   ```text
   deadline = now() + 上限
   while now() < deadline:
       if 条件满足: break
       sleep(3s)          # 短间隔，不是一次睡满
   ```

4. **单次等待要有上限，超了要报告。** 单次 sleep 超过约 30 秒，或同一等待重复超过两轮，就换成带上限的短轮询，并说明在等什么；真被卡住时报告「等了多久、在等什么、观察到什么」，不要静默睡满。这条约束的是**单次 sleep 的时长**，不是等待总时长：事件式等待（如阻塞读某作业结果）可以有更长的单次上限，但同样要有界并说明在等什么——子代理编排里的有界等待另见 `skills/execute-plan/references/task-loop.md`。
5. **判断等待是否浪费，看时间线。** 等完记下起止时间（如 `Get-Date` / `date +%T`）。没有这行证据，就不算验证过等待策略。

## 本机实测（DSH，2026-10-16）

- 12 秒后台任务，全程不调用任何读取接口 → 收到完成通知，**不轮询也能拿到结果**。
- 12 秒前台命令设 5 秒超时 → 控制权约 5 秒就返回，随后同样收到完成通知。

**这两个观察证明的是「无需轮询即可拿到通知」，不证明「空闲干等会被叫醒」**：通知恰好在 agent 活跃期间到达，而同一 harness 上另一个会话在结束前先查了一次状态，就没再自发收到通知（解释不唯一）。所以真正空闲时用**阻塞式读取**（如 `job_output(wait=true)`）而不是押注被动唤醒；探针失败就退回带上限的短轮询。

结论：**「等命令结束」不需要 sleep，「等条件满足」才需要短轮询。** 换宿主或换 harness 时先复测探针，不要照搬。
