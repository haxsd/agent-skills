# 并行代理（Parallel Agents）

并行是资源换时间的策略，不是默认工作方式。先探测宿主能力，再决定是否并行、如何隔离、如何整合。

## 先探测能力

| 能力 | 需要的证据 | 不具备时 |
|---|---|---|
| 子代理派发 | 当前工具 schema 或宿主文档 | 顺序执行，不伪装并行 |
| 真实并发 | 宿主明确支持同时运行的执行单元；实际观察到的并发结果 | 批量排队不算并行，报告真实模式 |
| 写入隔离 | 原生工作区、独立 worktree、独立副本或只读共享 | 只做只读并行，或退回顺序 |
| 分支/worktree 副作用 | 用户已授权，或当前工作流明确要求 | 不创建分支、worktree |
| 合并、推送、清理 | 用户明确选择或原任务已授权 | 保留结果，等待决定 |

两个容易误判的点：

1. 把多个任务写进同一条消息，不自动等于它们会并发执行；以工具文档和实际调度为准。
2. 子代理有独立上下文，不等于有独立文件系统；共享工作树时仍会互相覆盖文件。

如果拿不到能力证据，按能力更弱的模式执行，并明确说明“当前是顺序/排队执行”，不要宣称已经并行。

## 模式 A：多个独立任务

### 适用条件

- 任务之间没有共享状态，处理一个不会改变另一个的输入或结论
- 每个任务都能独立定义成功标准
- 写入范围可以完全分开，或所有任务只读
- 某个任务失败不会让其他任务的结果失去意义

### 不适用

- 根因可能相同，修一个会改变另一个的诊断
- 需要先掌握整体状态，才能知道问题在哪
- 多个任务会改同一文件、同一锁、同一资源或同一分支
- 任务之间存在隐含接口，尚未定义

### 先画归属矩阵

派发前列出：

| 任务 | 读取范围 | 写入范围 | 共享资源 | 依赖 | 验证 |
|---|---|---|---|---|---|
| T1 | ... | ... | ... | ... | ... |
| T2 | ... | ... | ... | ... | ... |

同一路径只允许一个写入者。只读任务可以共享；需要写同一文件时，改成顺序执行或把该文件交给单一所有者。

### 派发方式

具体调用形式以当前宿主工具为准。不要照搬其他平台的 `Task(...)`、角色名或批量语法。每个工作者都应收到自包含说明：

```text
目标：完成哪个可独立验收的子任务
背景：复现步骤、错误信息、相关路径、验收标准
写入范围：只允许修改哪些文件/目录
禁止范围：不要改哪些共享文件，不要合并、推送或清理工作区
验证：必须运行哪些命令，什么输出算通过
返回：根因/方案、改动摘要、验证原文、未解决风险
```

派发数量按宿主并发额度和任务规模决定。不要为了“看起来并行”拆出大量微小任务；协调和审查成本可能更高。

### 整合

1. 先读每个工作者的实际 diff，不只看成功报告。
2. 检查路径和接口冲突，必要时按依赖顺序合并。
3. 对合并后的状态运行受影响的测试和构建，不把各分支的独立绿灯当成合并后证据。
4. 保留失败任务的结果，说明是重试、改派还是放弃。

## 模式 B：同一难题的多方案试验

### 适用条件

- 有 2–3 个真正不同的方案，而不是同一实现的措辞变体
- 不确定性高，先做小规模试验比继续讨论更快
- 每个方案都有可比较的成功判据、成本和风险
- 错误选择的代价足以覆盖隔离和整合成本

简单 bug、单一路径或低风险改动直接做，不套 best-of-N。

### 选择隔离方式

按以下顺序选择，前一项不可用才降级：

1. **宿主原生隔离**：宿主提供独立工作区、worktree 或专用试验运行器，且用户已授权。
2. **平台子代理 + 独立 worktree**：当前环境支持子代理和 git worktree，先确认基线提交与写入范围。
3. **独立副本**：不是 git 仓库，或不允许创建分支；复制到独立临时目录，禁止写回共享工作树。
4. **顺序试验**：没有任何隔离手段时，一次只改一个方案，保留 diff 或补丁，再恢复基线试下一个。

不要在没有隔离的情况下让多个方案同时写同一个工作树。

### 试验约束

- 所有方案从同一基线出发，记录基线提交或文件哈希。
- 规格和成功判据相同，只改变被验证的核心假设。
- 每个方案独立运行指定检查，报告原始输出和成本。
- 保留全部方案产物；不要试验结束后自动删除“失败者”。
- 结果非代码时（分析、文案、设计选项），明确比较维度和证据，不把主观偏好写成客观胜出。

### 选择与整合

1. 按预声明判据比较正确性、性能、可维护性、风险和成本。
2. 如果没有方案满足最低门槛，报告失败并重新定义问题；不要强行挑一个。
3. 胜出方案先审查 diff，再按补丁或明确文件范围整合；不要整目录覆盖共享工作树。
4. 合并后在目标状态重新运行关键检查。
5. 其余分支、worktree 和产物默认保留。清理或删除必须有用户授权，并遵守工作区成果保护规则。

## 常见错误

| 错误 | 修正 |
|---|---|
| 假定某角色名在所有宿主都存在 | 从当前工具 schema 取真实能力；没有就降级 |
| 多个任务写同一文件 | 指定单一所有者，或改为顺序 |
| 把批量排队说成并行 | 报告实际调度模式，不夸大吞吐 |
| 各任务测试都绿就宣布整合成功 | 在整合后的状态重跑受影响检查 |
| 自动合并胜者并清理其他分支 | 先比较、审查、确认，再按授权整合和清理 |
| 没有隔离还让方案互相写回 | 只读并行、独立副本或顺序试验 |
| 只信子代理的“已完成” | 检查 diff、命令输出和未解决风险 |

## 与 execute-plan 的分工

- `parallel-agents` 解决“哪些工作可以并行、如何隔离、如何比较和整合”。
- `execute-plan` 解决“按计划逐任务实现、审查和记账”的执行流程。
- 独立调查或方案试验可以用本技能；需要逐任务把关的实现仍由 `execute-plan` 负责。
