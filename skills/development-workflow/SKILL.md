# 开发工作流

## 计划与实施

1. 读取项目规则，定位现有实现、依赖和验收条件。先调查可自行查明的信息，只追问影响结果的缺口。
2. 小改动直接执行；多步骤任务记录简短计划。只有跨会话交接、用户要求或复杂依赖时才保存计划文件。
3. 每项计划写明结果、相关文件、依赖和验证方式；执行时根据现场证据修正，不机械照抄过时方案。
4. 采用项目现有测试策略。行为缺陷先复现；跨整个输入域的性质使用专项属性测试；纯文案、格式改动不强制测试先行。
5. 仅在需要隔离时建立工作区。检查现有改动，避免覆盖用户文件；基线失败先定位来源，继续能独立完成的工作。
6. 只有当前任务授权和宿主工具支持时才委派。独立任务可以并行，写入范围分开；验收真实 diff 与运行证据。

## 验证与交付

- 按风险选择测试、构建、类型检查、界面检查等必要验证；检查实际退出码和输出，不凭推测宣布完成。
- 将测试失败区分为本次引入、既有问题和环境问题；明确未验证的范围。
- 核对需求覆盖、diff、秘密信息和无关文件。只有新改动或未解决风险才扩大或重复验证。
- 用户已指定提交、PR 或交付方式时按授权执行；未授权合并、部署或删除时停在可审阅结果。
- Git 操作前核对仓库、分支、base 和远程。托管 worktree 使用宿主生命周期工具，只清理本次创建且不再需要的资源。
- 最终说明结果、关键验证和剩余限制，避免固定选项菜单和重复确认。

## 计划记录格式

复杂任务可记录：目标与验收条件；任务及依赖；修改位置；验证方式；尚未解决的问题。
不要预先重复写出整个实现，不强制逐步提交，不自动创建用户未要求的新聊天。
