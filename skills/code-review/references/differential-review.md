# 差异安全审查

审查一份差异（PR、提交区间或未提交改动）**引入**的安全风险。普通质量问题仍按入口的通用检查处理。
先定范围与基线，再按风险分级投入；结论要有历史、调用方或运行证据支撑。

## 何时读

- 差异触及认证/授权、加密、外部调用、值转移，或校验、权限检查的删改。
- 用户问"这个改动可能破坏什么""是否重新引入已修复缺陷""还有哪些调用方受影响"。

## 只读约束

- 用 `git show`、`git diff base..head`、`git log -S`、`git blame <rev> -- <path>` 读历史；**不 checkout 基线**（上游示例会切换版本）。需要另一版本工作副本时先取得授权，并放到独立临时目录。
- 不执行项目测试、构建、安装或工作流；静态结论与运行证据分开标注。
- 不修改被审代码；修复建议只写方向，不代改。

## 1. 分诊与覆盖预算

- 规模策略：相关文件 <20 深读依赖；20–200 读一跳依赖与优先文件；200+ 只看关键路径。先写下本轮覆盖预算与不读的范围。
- 文件风险：**高**＝认证、加密、外部调用、值转移、校验移除、权限修饰符变化；**中**＝业务逻辑、状态变更、新公开接口；**低**＝注释、测试、UI、日志。
- 不按 diff 行数定风险，按语义；"只是重构"按高风险分析，直到证明为低。

## 2. 逐区读改动

- 对每个差异区域记录：BEFORE / AFTER / 行为变化 / 安全含义。
- 删除的代码做历史定位：`git log -S "<片段>" --all --oneline`；关注 message 含 fix/security/CVE 的提交，以及近期新增后又被删除的代码。
- 校验、权限检查、边界检查被移除时，确认是否有等效替代；没有就列为回归候选。
- 曾被安全修复的代码重新出现＝回归，重点核对。与基线不变量对照：原来必须始终成立的性质，改动后是否仍成立。

## 3. 测试覆盖

- 改动函数是否有对应测试；新增函数无测试、校验被改而测试未动时提高风险评级。
- 缺测试写成修复建议，不当作漏洞本身，也不替代可达性证据。

## 4. 影响面

- 统计被修改函数/接口的调用方（用宿主搜索，不安装新工具），分级：1–5 低，6–20 中，21–50 高，50+ 严重。
- 高影响 × 高风险优先深读；调用方数量是线索，不自动等于可利用性。

## 5. 高风险改动做对抗分析

- 攻击者模型：谁（未认证外部用户/认证用户/管理员/被攻陷服务）、有什么权限、从哪个入口进入。
- 攻击链：入口 → 参数与前置状态 → 到达脆弱点 → 影响；给出具体步骤，并评级 EASY（公开接口即可）/ MEDIUM（需要条件或时序）/ HARD（需特权或罕见条件）。
- 与基线对照：违反哪条不变量、跨过哪条信任边界、绕过哪道校验。写清是本次引入还是基线既有；基线既有风险只在本次改动使其可达时计入。

## 6. 输出

- 每个发现：严重程度与置信度（分开）、`file:line`、版本/提交、影响面、测试覆盖、攻击场景（不是"可能存在风险"）、修复方向。
- 报告覆盖：策略与预算、读过与未读范围、置信度、下一步需要的证据；零发现也要说明方法，不外推"全仓没有此类问题"。
- 默认在回复中交付；用户要求落盘报告或发布评论时再按其授权执行。

## 快速升级信号

- fix/security/CVE 提交中的代码被移除或改弱；访问控制修饰符被移除；校验移除且无替代；新增外部调用无检查；高影响面叠加高风险改动；不可信输入被直接交给解释器（shell/SQL/模板/反序列化）。

## 衔接

- 已确认根因、要在别处找同族实例：转 variant-analysis（本文件只看当前差异，不扩为全仓排查）。
- 凭据字段与序列化汇点：读同目录 [secret-serialization.md](secret-serialization.md)。
- 工作流与 CI 差异：读同目录 [github-actions.md](github-actions.md)。
- 故障原因未知：先 systematic-debugging。
