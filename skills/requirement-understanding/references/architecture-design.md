# 架构路径参考

供 requirement-understanding 的架构路径使用：方案比较、设计呈现、规格自检。

## 方案比较

- 只提真实存在分歧的方案，2~3 个，不要罗列凑数
- 每个方案给出代价、收益和适用条件；先给推荐项和理由
- YAGNI 全程执行：从每个方案里删掉没有被要求的特性
- 方案讨论留在对话里；结论写进规格文档

## 设计呈现

- 按复杂度决定篇幅：简单部分几句话，复杂部分 200~300 字
- 每节确认一次再继续（"到这里对吗？"）
- 覆盖：架构、组件、数据流、错误处理、测试

## 设计隔离与清晰

- 拆成单一职责的小单元：能用一句话说清它做什么、怎么用、依赖什么
- 能不看内部实现就理解单元用途；能改内部而不破坏调用方——否则边界要重划
- 在现有代码库里：先探索再提议；跟随现有模式；顺手改进影响本任务的明显问题，不做无关重构

## 规格自检（写完规格后）

1. 占位符扫描：TBD、TODO、含糊需求——修掉
2. 内部一致性：各节是否互相矛盾；架构与功能描述是否一致
3. 范围检查：是否适合单个实施计划，还是需要拆分
4. 歧义检查：是否有需求能被两种方式解读——选定一种写明确

修掉即可，不必重审；随后请用户审查规格文件。需要独立审查时，用 [spec-reviewer-prompt.md](spec-reviewer-prompt.md) 派发规格审查子代理。
