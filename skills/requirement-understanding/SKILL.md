# 需求理解与方案分流

收到需求先理解、再分流、后执行。流程随复杂度伸缩，简单任务不要套重流程。

## 第 1 步：分流（先说结论，允许用户推翻）

- **明确任务** — 目标、位置、做法都清楚（一行文案、明确的 bug、已定方案的小改动）：直接执行，一句话说明打算怎么改，不追问、不写文档。
- **有界任务** — 改动范围明确但存在真实选择（接口、数据形状、边界行为）：问最少的关键问题，在对话里给简短方案（几句话），得到认可后动手；不写规格文档。
- **架构任务** — 新项目、新子系统、改变组件边界或对外接口的改动：走完整流程——问题澄清 → 2~3 个真实方案比较 → 分节设计 → 写规格 → 交 writing-plans 写计划。

判断标准：**有界看仓库里有没有可直接读的现有流程**（没有＝不是有界）；架构看是否重排组件关系或对外接口。拿不准时选更重的路径；中途发现隐藏复杂度就升级路径并说明，不要降级。

用户已明确授权直接执行时，按明确任务处理，不重复确认。

## 第 2 步：先理解，再动手

1. 通读需求，提炼目标、涉及功能/模块、期望结果。
2. 结合项目定位需求：浏览结构、读相关代码、理解现有实现与约定。
3. 判断影响范围：哪些文件要改、项目里是否已有类似实现可参考。
4. 描述和代码都看过之后，才判断理解是否充分。

## 第 3 步：不明确就追问

以下任一情况先问，不实现：目标不明确、完成标准不明确、范围不明确、约束不明确、有多种合理解释。

追问技巧：

- 一次只问最关键的 1~5 个问题，优先问能排除整条歧路的问题
- 简短、编号、可快速扫读；能提供选项就提供选项
- 用「编号 + 字母选项」列出可选项，约定简洁回复格式（如 `1b 2a`，或回复 `defaults` 接受全部推荐项）
- 给出推荐默认值和快速通道
- 能通过读代码查明的信息（配置、现有模式、文档），不要拿来问用户
- 只有影响结果的必需信息缺失才等待，其余调查继续

## 第 4 步：执行前复述理解

- 简单、低风险：复述后注明「如果没有异议我就开始」，继续执行
- 中大型或影响面广：复述后等用户确认（或纠正）再动手
- 用户明确说「不用确认，直接做」时，边复述边动手

```
我对需求的理解：
1. 要做什么：……
2. 涉及位置：<文件/模块列表>
3. 计划改动：……（简要说明）
4. 完成标准：……
```

## 架构路径：方案与规格

架构任务在前四步之外，还要做真实取舍和可验证的规格：

1. 检查项目现状（文件、文档、近期提交）；需求包含多个独立子系统时先帮助拆分，再对第一个子系统走完整流程
2. 一次一个问题地澄清目的、约束、成功标准
3. 提 2~3 个真实存在分歧的方案，带取舍与推荐（先给推荐项和理由）
4. 分节呈现设计，逐节确认
5. 把确认过的设计写成规格文档（默认 `docs/specs/YYYY-MM-DD-<topic>-design.md`，遵循项目惯例；提交与否按用户要求或项目约定），自检后请用户审查
6. 规格通过后交给 writing-plans 写实施计划；架构路径的终点是 writing-plans，不要再调用其他实现技能

方案比较、设计自检、规格审查的详细清单见 [references/architecture-design.md](references/architecture-design.md)。

## 反模式

- 一上来就写代码，跳过理解步骤
- 把能通过读代码确认的问题抛给用户
- 给明确的小任务套规格文档和多轮审批
- 一次问一堆开放式问题；不用选项和默认值
- 架构任务只罗列选项，不给真实取舍和推荐
- 在已有明确授权时反复请求批准
