# 需求理解（Requirement Understanding）

## 何时使用

每当用户提交一个项目需求或代码需求（新功能、改动、修复、重构等）时，都要先走完本流程，再开始实现。适用于所有项目。

## 工作流程

### 第 1 步：先理解，再动手

在写任何代码或执行任何命令之前：

1. 通读用户的需求描述，提炼出：目标、涉及的功能/模块、期望结果。
2. 结合当前项目情况定位需求：
   - 浏览项目结构，找到相关的文件、模块、配置。
   - 阅读相关代码，理解现有实现、命名风格和架构约定。
   - 判断需求影响范围：哪些文件要改、项目里是否已有类似实现可参考。
3. 只有在需求描述和代码都看过之后，才判断自己的理解是否充分。

### 第 2 步：不明确就追问

如果存在以下任一情况，先向用户提问，不要开始实现：

- 目标不明确：要改什么、保持不变的是什么
- 完成标准不明确：怎么算做完（验收标准、示例、边界情况）
- 范围不明确：涉及哪些文件/组件/用户
- 约束不明确：兼容性、性能、风格、依赖、环境等
- 有多种合理解释，无法确定用户想要哪一种

追问技巧：

- 一次只问最关键的 1~5 个问题，优先问能排除整条歧路的问题
- 问题简短、编号、可快速扫读；能提供选项就提供选项
- 用「编号 + 字母选项」列出可选项，并约定简洁回复格式（如 `1b 2a`，或回复 `defaults` 接受全部推荐项）
- 给出推荐默认值，并支持快速通道（如回复「defaults」/「按默认」即接受全部推荐项）
- 能通过快速读代码自己查到的信息（配置、现有模式、文档），不要拿来问用户

> 备注（维护者）：更完整的提问模板历史上放在 `archive/skills/ask-questions-if-underspecified/`，未随默认安装；agent 不应依赖它存在，使用上面的内联技巧即可。

### 第 3 步：执行前复述理解

开始实现之前，先向用户复述自己的理解，建议用下面的格式：

```
我对需求的理解：
1. 要做什么：……
2. 涉及位置：<文件/模块列表>
3. 计划改动：……（简要说明）
4. 完成标准：……
```

确认方式：

- 简单、低风险的改动：复述后注明「如果没有异议我就开始」，然后直接继续。
- 中大型或影响面广的改动：复述后等用户确认（或纠正）再动手。
- 用户明确说「不用确认，直接做」时，边复述边动手即可。

## 反模式

- 不要一上来就写代码，跳过理解步骤。
- 不要把能通过读代码确认的问题抛给用户。
- 不要问一堆开放式问题；用选项和默认值降低用户的回答成本。
- 极小的改动（如改一句文案）可以不严格走完整流程，但仍需用一句话说明打算怎么改。
