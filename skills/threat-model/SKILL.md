# 威胁建模

目标是“这个仓库在真实用法下最可能怎样被滥用”，不是通用漏洞清单。每条架构判断都要有仓库证据（路径 + 符号/配置键/短引用）；没有证据就写成假设。

## 0. 定范围

- 范围：整个仓库还是某个子路径；明确排除项。
- 运行形态：服务、CLI、库、worker、桌面应用、agent/bot；入口在哪。
- 已知上下文：部署方式、是否暴露到公网、认证预期、数据敏感度、多租户。不知道的先推断并标“假设”。
- 区分三类代码：运行时 / CI·构建·发布 / 测试与示例。只有 CI 能触达的问题按 CI 的攻击者算。
- 区分三类输入：攻击者可控 / 运维可控 / 开发者可控。需要攻击者控制运维输入才成立的威胁要降级并说明。

## 1. 取证

用 `rg -I` 找安全相关面，每类挑 1~2 个锚点即可，不倾倒全部匹配：

- 网络监听、路由、RPC/消息消费者、webhook
- 认证、会话/令牌、授权检查（RBAC/ACL）
- 解析与反序列化（JSON/YAML/XML/pickle）、模板渲染、`eval`/动态执行
- 文件上传/读取、归档解压、文档/图像解析
- 数据库/队列/缓存客户端与查询拼接
- 密钥与配置加载、环境变量
- 能发起出站请求的代码（SSRF）、URL 抓取器
- 子进程执行、沙箱/隔离、权限边界
- 日志与错误输出（是否泄露密钥或个人数据）
- CI/发布：workflow 触发器、第三方 action、制品发布、依赖锁定

LLM/agent 应用额外读 [references/llm-agent-threats.md](references/llm-agent-threats.md)。

## 2. 系统模型

- 主要组件与数据存储。
- 信任边界写成箭头：`来源 → 目标`，每条注明穿越的数据（凭据、个人数据、文件、prompt、工具调用）、通道（HTTP/IPC/文件/DB/模型 API）、现有保证（认证、来源校验、加密、限流、schema 校验）。
- 一张紧凑的 Mermaid 图：`flowchart LR`，只用 `-->`，节点 ID 只含字母数字下划线、标签加引号，不放路径和 URL，不用 `title`/`style`。

## 3. 资产与攻击者

- 资产表：资产 | 为什么重要 | 目标（机密性/完整性/可用性）。
- 攻击者能力：按暴露面写现实的能力。
- **非能力**：明确写出攻击者做不到的事（例如“无法登录维护者机器”“不能修改仓库 secrets”），防止严重度膨胀。

## 4. 滥用路径与排序

- 5~10 条滥用路径，每条写成“目标 → 步骤 → 影响”，优先多步、跨边界的路径。
- 每条给可能性和影响（低/中/高 + 一两句理由），综合成 critical/high/medium/low，并扣除已有控制。
- 写出最影响排序的 1~3 个假设。

## 5. 先核对假设，再出终稿

终稿前先给用户：3~6 条关键假设 + 1~3 个针对性问题（部署方式、谁能访问、数据敏感度、多租户、认证方式）。等回答；用户不答或答不了，就带着显式假设继续，并把受影响的建议标为“有条件”。

## 6. 缓解与重点路径

- 区分**已有控制（附证据）**与**建议控制**。
- 建议落到具体位置和控制类型：“在 `api/upload.py` 的入口按 schema 校验并限制大小”，而不是“做好输入校验”。
- 高/严重威胁补检测思路（日志、指标、告警）。
- 列 2~30 个值得人工深审的路径，每个一句理由并关联威胁 ID。

## 7. 产出与自检

按 [references/output-contract.md](references/output-contract.md) 的章节顺序写 `<仓库或目录名>-threat-model.md`：项目有安全文档目录就放那里，否则放用户指定位置或系统临时目录，并告知路径。不把威胁模型提交到公开仓库，除非用户明确要求。

交付前自检：

- 发现的每个入口都被覆盖；每条信任边界至少出现在一条威胁里。
- 运行时与 CI/开发分开；攻击者可控与运维可控输入分开。
- 用户的澄清（或未答）已反映在排序里；假设和未决问题显式列出。
- 报告里没有任何密钥原文：只写“存在于何处”。
