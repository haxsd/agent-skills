# 提交信息与 PR 描述

改编自 getsentry/skills 的 `commit` 与 `pr-writer`（固定版本 0c464f411bdfb8d4c12314b36264d06cb2f60270，Apache-2.0，Copyright 2025 Functional Software, Inc. dba Sentry；完整许可见 `../LICENSES/Apache-2.0.txt`）。本仓中文改写：仓库已有约定优先，去掉 Sentry 专有的 issue 格式与默认草稿规则。

## 先看仓库约定

`git log --oneline -20` 看最近的提交：语言（中文/英文）、是否用 `type(scope):` 前缀、是否引用 issue。照现有风格写；没有明显风格时用下面的默认写法。贡献指南或 PR 模板存在时以它为准。

## 提交信息

- 一次提交一个能独立审查的改动；无关改动分开提交。
- 默认格式 `<type>(<scope>): <subject>`，type 取 `feat` `fix` `ref` `perf` `docs` `test` `build` `ci` `chore` `revert` 等；破坏外部契约时在冒号前加 `!` 并在正文写影响。
- 标题写“做了什么”，不超过约 70 个字符，不加句号；正文只在有用时写：之前的行为、为什么改、对使用者的影响。
- 关闭 issue 用 `Fixes #123`，只关联用 `Refs #123`；issue 号必须来自用户、分支名、提交或 tracker，不要猜。
- 不写客户/组织名、邮箱、工单内容、密钥、本机路径或内部账号；用技术症状代替。
- 用多个 `-m` 分段或 `-F <文件>`，不要在消息里写字面 `\n`，也不要打开交互式编辑器。

## PR 标题与描述

先看整个分支，而不是最后一个提交：

```bash
git log "$BASE"..HEAD --oneline
git diff "$BASE"...HEAD --stat
```

- 标题描述整个分支的主要改动，格式同提交标题；避免“update”“cleanup”“address feedback”这类空标题。
- 描述是写给审查者的说明，不是变更日志：先写行为变化和影响面，再写必要的动机、风险、取舍、迁移方式或建议从哪里开始看。
- 结构按需最小化：

| 改动 | 写什么 |
|---|---|
| 小而明显 | 一段话，不加标题 |
| 功能、修复、重构 | 行为变化与效果；必要时补根因、未变的行为、非显而易见的做法 |
| 契约或破坏性变更 | 受影响的 API/配置/CLI/存储面，兼容性与迁移步骤，前后对比的小例子 |
| 大范围或生成的改动 | 组织原则、为什么必须这么大、审查从哪里入手 |

- 不默认加“Summary / Changes / Test Plan”空壳；常规验证不必罗列，只有影响风险判断时才写，并给结论而不是粘日志。
- 不贴整段命令输出、CI 日志、提交列表或完整文件清单。
- 后续提交明显改变范围、方案、风险或迁移方式时，按当前完整 diff 重写标题和描述，不叙述评审过程；只是错字或格式修正不必改。
- 描述写进临时文件再用 `gh pr create --body-file <文件>` 或 `gh pr edit <号> --body-file <文件>`，避免 shell 转义问题。创建为草稿还是正式 PR、是否请求审查，按用户或仓库约定。
